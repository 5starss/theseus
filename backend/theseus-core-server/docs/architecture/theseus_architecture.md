# 테세우스(Theseus) 프로젝트 종합 기획 명세 및 아키텍처

본 문서는 사내 맞춤형 AI 에이전트를 구축하고자 하는 기업 및 개발 조직을 위한 B2B/오픈소스 플랫폼 **'테세우스(Theseus)'**의 기획 배경, 타겟 페르소나, 그리고 시스템 아키텍처를 정의합니다. (OpenHarness 코어 래핑 및 Java Spring Boot 백엔드 기반)

---

## 1. 기획 배경 (Background & Vision)

최근 LLM을 이용한 에이전트 시스템(Tool 활용)의 도입과 사용량이 폭발적으로 증가하고 있습니다. 하지만 이러한 발전은 두 가지 심각한 현실적 문제에 직면해 있습니다.

1. **컨텍스트 윈도우 한계와 비용 증가**: 프롬프트에 수많은 도구(Tool)의 스키마와 사용법, 사내 시스템 접근 절차 등을 길게 명시하다 보니, 매 턴마다 소모되는 토큰량이 기하급수적으로 늘어나 비용이 증가하고 모델의 컨텍스트 한계에 빠르게 도달합니다.
2. **보안 및 통제력 부재**: 권한 없는 사용자가 에이전트를 통해 민감한 데이터를 조회하거나 수정(DB 삭제 등)할 수 있는 보안 리스크가 큽니다.

**테세우스(Theseus)의 해결책:**
* **메타-툴링(Meta-Tooling)을 통한 컨텍스트 압축**: 반복적이고 긴 시스템 사용 절차를 자연어를 통해 단일 '도구(Tool)' 코드로 캡슐화(생성)합니다. 에이전트는 긴 설명을 읽는 대신 툴 하나만 호출하면 되므로 토큰 사용량이 극적으로 감소합니다.
* **RBAC(역할 기반 접근 제어) 기반 프롬프트 필터링**: 사용자 등급에 따라 접근할 수 없는 툴은 에이전트의 프롬프트 정보에서 아예 제외합니다. 이를 통해 **추가적인 컨텍스트 감소(비용 절감)**를 꾀하고, 권한 밖의 작업을 원천 차단하여 **보안성**을 극대화합니다.

---

## 2. 타겟 페르소나 (Target Persona)

* **도입 주체**: AI 에이전트 시스템에 대한 깊은 전문 지식은 없지만, **자사 서비스 및 팀의 업무 프로세스에 완벽하게 특화된 AI 에이전트를 구축하고 싶은 기업의 IT 관리자 및 시니어 개발자**.
* **엔드 유저**: 팀 내 규정된 도구를 사용하여 실무를 수행하는 일반 사원 및 개발자.
* **가치 제안 (Value Proposition)**: 
  * "전문 AI 엔지니어 없이도, 자연어만으로 우리 팀만의 도구를 만들고, 안전한 권한 제어 아래 팀원들에게 AI 에이전트를 배포하세요."

---

## 3. 시스템 아키텍처 오버뷰 (System Architecture Overview)

테세우스 시스템은 관리 편의성과 에이전트 활용성을 극대화하기 위해 **관리용 웹(Web UI)**과 **실행용 CLI**로 분리된 하이브리드 인터페이스를 채택하며, 실시간 스트리밍 처리를 지원합니다.

* **Core Engine**: OpenHarness 라이브러리 래핑 (프롬프트 구성, 에이전트 실행, 도구 호출 처리)
* **Backend API Server**: Java Spring Boot 기반 (인증, DB 연동, 비즈니스 로직 및 Python Core 제어)
* **Frontend (Web UI)**: 도구(Tool) 승인/관리, 프로젝트 생성, 팀원 권한 관리 대시보드
* **Client (CLI)**: 일반 사용자가 할당된 프로젝트 내에서 에이전트(테세우스)와 소통하고 도구를 실행하는 창구
* **통신 프로토콜**: REST API (CRUD 관리) + **WebSocket / SSE** (실시간 LLM 스트리밍)

## 4. 핵심 도메인 구현 설계 (Core Domain Specs)

### 4.1 사용자 및 인증 관리 (USR)
* **인증 시스템**: JWT 기반 토큰 인증 (로그인/로그아웃/세션 관리).
* **최고 관리자 (SuperAdmin)**: MVP 단계에서는 스크립트로 초기 1회 생성. 사용자(Staff) 신규 등록/수정 전권 보유.
* **전역 직급(Role)**: `ADMIN`, `MANAGER`, `USER` 등급 부여 및 UI 상시 노출.
* **실행 전 검사 (Hook)**: OpenHarness의 툴 실행 전 사용자 등급 기반 실행 가능 여부 검증.

### 4.2 프로젝트 관리 (PRJ)
* **테넌트 격리**: 프로젝트 단위로 데이터를 분리하며, 사용자는 할당된 프로젝트만 접근 가능.
* **프로젝트 단위 RBAC**: 프로젝트별 사용자 할당 및 역할(Role) 부여 (접근 제어 필수).

### 4.3 도구 생성 및 생명주기 관리 (TOOL)

#### A. 물리적 폴더 구조 및 격리
* **`basic_tools/`**: 테세우스 시스템이 기본 제공하는 코어 도구(예: `tool_write`, `tool_read`, 검증 도구 등).
* **`custom_tools/{project_name}/`**: 사용자가 메타-툴링으로 생성한 프로젝트별 전용 도구 및 스킬(`.md`)이 저장되는 격리 공간.

#### B. 생성 및 승인 파이프라인 (Interactive Planning & HITL)
* **1단계: 플래닝 및 인터랙티브 리뷰 (Planning Mode)**
  * 사용자가 자연어로 요구사항을 입력하면, 에이전트가 즉시 코드를 짜는 대신 **단계별 상세 구현 계획(Plan)**을 먼저 작성하여 제시합니다.
  * 사용자는 계획을 리뷰하고 틀린 부분이나 추가 사항을 피드백합니다. 에이전트는 피드백을 반영해 계획을 수정하며, 사용자가 **최종 승인(Accept)**할 때까지 이 과정을 반복합니다.
* **2단계: 코드 생성 (Drafting)**: 사용자가 승인한 완벽한 계획을 바탕으로 실제 작동하는 Python `BaseTool` 코드를 생성합니다.
* **3단계: 1차 자동 검증 (Tool Validators)**: 생성된 코드를 위험도와 용도에 따라 4종의 세분화된 검증기(Execution, Query, Analysis, Suggestion)가 다각도로 스캔하여 취약점 탐지 및 성능 개선을 제안합니다.
* **4단계: 상태 관리 및 최종 승인 (Admin Review)**
  * 도구의 상태는 `Draft` -> `Pending` -> `Approved` 순으로 관리됩니다.
  * 자동 검증을 통과한 `Pending` 상태의 코드를 관리자(최고 권한자)가 Web UI에서 최종 확인 및 수동 편집한 뒤 `Approved` 처리해야 시스템에 완전히 등록됩니다.

#### B. 권한 및 접근 제어 (RBAC on Tools)
* **권한 상속**: 생성자의 권한을 기본 상속.
* **세분화된 정책**: 도구별 `생성/조회/수정/삭제/실행` 권한 제어.
* **정밀 권한 통제**: 필요시 Tool 내부의 파일(File) 또는 DB의 Row 단위까지 ACL 적용 가능.

#### D. 버전 및 이력 관리
* **버전 컨트롤**: `v1`, `v2` 등 버전 생성 및 Web UI에서의 **Diff 시각화**.
* **실행 제어**: 특정 버전을 선택하여 실행(롤백) 가능 기능 제공.

#### E. 툴 라이프사이클 및 유지보수 (Maintenance & Auto-Healing)
* **고장 감지**: 사내 API 스펙이나 DB 스키마 변경으로 커스텀 도구에 에러가 지속 발생할 경우, 실패율을 모니터링하여 관리자에게 알림을 전송합니다.
* **자동 복구 파이프라인**: 에러가 감지된 툴에 대해, 에이전트가 변경된 환경을 바탕으로 코드를 스스로 수정 제안하는 자동 업데이트 루프를 가동합니다.

### 4.4 모니터링 및 보안 가드레일 (Monitoring & Security)
* **비용 절감 시각화 UI (Token ROI Dashboard)**:
  * 테세우스를 사용하지 않고 프로젝트 내 모든 툴을 로드했을 때의 **'예상 토큰량'** vs RBAC를 통해 필터링된 현재 등급 사용자의 **'실제 토큰 소모량'**을 비교하는 차트 제공. 고객이 비용 절감 효과를 즉각 체감 가능.
* **프롬프트 인젝션 방어 (Guardrails)**:
  * 도구(Tool) 호출 시 Jailbreaking 방지를 위한 강력한 경고성 시스템 인스트럭션 주입.
  * Pydantic을 활용한 엄격한 파라미터 타입 검증 로직 필수 적용.

### 4.5 비즈니스 모델 (Tiering Strategy)
* **Community Edition (OSS)**: 기본 RBAC 및 자연어 도구 생성 프롬프트 제공.
* **Enterprise Edition (B2B)**: Row-level ACL, SSO/SAML 연동, 감사 로그(Audit Logs), 고급 Diff UI 및 비용 절감 대시보드 제공.

## 5. 연동 전략 (Spring Boot - Python Core MSA)

Java Spring Boot 백엔드가 비즈니스 로직을 통제하고, 실제 AI 연산은 OpenHarness(Python) 코어 서버와 통신하는 **마이크로서비스(MSA)** 형태로 설계합니다.

1. **상태 주입 (State Injection via API)**
   * 클라이언트가 Spring 백엔드에서 1회성 세션 토큰을 발급받습니다. 이 과정에서 `user_id`, `project_id`, `role_id`가 검증됩니다.
   * 접근 가능한 `Approved` 도구 목록만 추려 Python 코어 엔진에 주입 (이 과정에서 권한 없는 도구가 프롬프트에서 탈락하여 **컨텍스트 대폭 감소**).
2. **다이렉트 스트리밍 및 Zero-Trust 과금 (Direct Streaming via Token)**
   * **(병목 방지)**: 무거운 LLM 스트리밍 트래픽이 Spring Boot를 거칠 경우 커넥션 풀이 고갈될 위험이 큽니다.
   * 클라이언트는 발급받은 세션 토큰을 들고 **Python 코어 서버(FastAPI)와 직접 WebSocket/SSE 통신**을 맺어 실시간 응답을 받습니다.
   * **(과금 무결성)**: 토큰 소모량은 클라이언트를 거치지 않고 스트리밍 종료 시 Python 서버가 내부망을 통해 Spring Boot로 직접 전송(Server-to-Server)하여 과금 어뷰징을 원천 차단합니다.
3. **인터셉터 및 샌드박스 (Sandbox & Callbacks)**
   * Python 코어가 도구를 실행하기 직전, Spring 백엔드의 권한 검증 API를 콜백하여 2중 보안 체크를 수행합니다.
   * 승인된 코드라도 보안을 위해 **Docker-in-Docker** 형태의 격리된 샌드박스 환경에서 실행됩니다.

## 6. 확장 아키텍처: RAG 및 멀티 에이전트 지식 기반 (Advanced Architecture)

테세우스의 세션이 누적되고, 프로젝트별 사내 문서가 많아질 경우를 대비하여 **VectorDB 및 RAG(Retrieval-Augmented Generation)** 파이프라인 도입을 고려해야 합니다.

### 6.1 VectorDB 기반 지식 파이프라인
* **한계 극복**: OpenHarness의 기존 메모리 시스템은 단순한 키워드 매칭(Heuristic Search) 방식입니다. 이를 **ChromaDB** 또는 **Milvus**와 같은 VectorDB로 교체하여 시맨틱 검색(Semantic Search)이 가능하도록 구축합니다. (스케일 아웃을 위해 로컬 파일 모드가 아닌 Client-Server 모드로 연동)
* **지식 캡슐화**: RAG 검색 자체를 모든 프롬프트에 강제로 주입하지 않고, `search_knowledge_base`라는 별도의 도구(Tool)로 캡슐화합니다. 에이전트가 필요하다고 판단할 때만 호출하여 불필요한 컨텍스트 비용을 최소화합니다.

### 6.2 지식 전담 에이전트 분리 (Knowledge Agent)
* **멀티 에이전트 오케스트레이션**: 작업을 수행하는 Worker 에이전트와 지식을 검색하는 Knowledge 에이전트를 분리합니다. 
* Coordinator 에이전트가 사용자의 질문을 분석한 뒤, 과거 지식이 필요하다면 Knowledge 에이전트에게 VectorDB 검색을 지시하여 요약된 정보만 받아내고, 이를 Worker 에이전트에게 전달하는 분업화된 구조를 설계합니다.

### 6.3 LangSmith 연동을 통한 관측성 (Observability)
* 멀티 에이전트와 RAG가 결합되면 에이전트의 사고 흐름(어떤 문서를 찾았고, 어떻게 판단했는지)을 추적하기 매우 어려워집니다.
* **해결책**: 백엔드와 코어 로직 전반에 **LangSmith**의 `@traceable` 데코레이터를 적용합니다. 관리자는 LangSmith 대시보드를 통해 에이전트의 툴 호출 트리, 검색된 RAG Chunk 원문, 토큰 소모량을 시각적으로 디버깅하고 성능을 평가(Evaluation)할 수 있습니다.
