# Theseus 코어 시스템 아키텍처 및 보안 개선 로드맵 (Agent-Generated)

**작성자:** Theseus AI Agent
**작성일:** 2026-04-27
**문서 목적:** B2B 엔터프라이즈 프로덕션 환경 도입을 앞두고, 현재 구현된 Theseus 코어 시스템의 치명적인 아키텍처 결함 및 보안 취약점을 냉철하게 자체 분석하여 향후 개발 우선순위 및 개선 방향을 제안합니다.

---

## 1. 🚨 보안: AST 정적 분석의 한계와 Sandbox 격리 최우선화

### 1.1. 현재 문제점 (취약 상태)
현재 메타-툴링(`ToolCreatorTool`)을 통해 생성된 코드는 FastAPI 워커와 동일한 메모리 공간에 로드됩니다. `ast` 모듈을 이용해 `os`, `subprocess` 등을 필터링하고 있으나, 파이썬의 동적 특성(리플렉션, `__import__` 등)을 이용한 우회 공격에는 무방비 상태입니다. 악성 코드나 버그가 포함된 툴이 무한 루프나 메모리 누수를 일으키면 메인 FastAPI 서버 전체가 다운되는 치명적 위험이 존재합니다.

### 1.2. 개선 방안
- **로컬 실행 전면 금지**: 사용자가 생성한 커스텀 도구 코드가 메인 서버 프로세스 내에서 실행되는 구조를 즉시 폐기합니다.
- **격리 환경(Sandbox) 구축 최우선화**: 기존 MVP 후순위로 미뤄뒀던 샌드박스(DinD 기반 격리 컨테이너 또는 AWS Lambda와 같은 Serverless)를 0순위로 도입하여, HTTP/gRPC를 통해 실행 결과만 반환받도록 아키텍처를 전면 수정해야 합니다.

## 2. 💸 데이터 정합성: Zero-Trust 과금 처리의 허술함

### 2.1. 현재 문제점
LLM 스트리밍 종료 후 FastAPI의 메모리 기반 `BackgroundTasks`를 통해 Spring Boot 내부망으로 과금(Token Usage) 정보를 쏘는 구조입니다. 만약 처리 중 OOM(Out of Memory)으로 Pod가 죽거나 서버가 재시작되면, 해당 세션의 과금 데이터는 영구적으로 증발(Data Loss)합니다.

### 2.2. 개선 방안
- **메시지 큐(MQ) 도입**: 엔터프라이즈 트랜잭션의 신뢰성을 보장하기 위해 `BackgroundTasks`를 폐기하고, Redis Pub/Sub, RabbitMQ, 혹은 Kafka와 같은 신뢰성 있는 메시지 큐 시스템을 도입해야 합니다.
- **배치(Batch) 처리 폴백 마련**: 로컬 DB에 과금 내역을 1차 기록한 후 주기적으로 Spring Boot와 동기화하는 안정적인 폴백(Fallback) 아키텍처가 필요합니다.

## 3. 💣 상태 동기화 및 기술 부채 (Monkey-Patching)

### 3.1. 동적 로딩(importlib)의 한계
다중 워커(Multi-worker) 환경에서 파일 시스템(`custom_tools/`)에 의존해 툴을 동적으로 로드하면, 워커 간 메모리 상태 불일치가 필연적으로 발생합니다. (A 워커는 툴을 인식하나 B 워커는 에러 반환)
**개선 방안:** 파일 시스템 의존을 버리고, 메타-툴링으로 생성된 코드와 메타데이터를 PostgreSQL 등 중앙 DB에 저장한 후 실행 시점에 격리 환경으로 주입하는 방식으로 변경해야 합니다.

### 3.2. 몽키패칭(Monkey-Patching) 청산
Gemini 호환성을 위해 OpenHarness 내부 함수(`_stream_once` 등)를 런타임에 덮어씌운 것은 라이브러리 마이너 업데이트 시 서버가 뻗어버릴 수 있는 최악의 기술 부채입니다.
**개선 방안:** 코어 엔진에 PR을 보내 공식적으로 버그를 픽스하거나, 엔진을 래핑하는 별도의 어댑터(Adapter) 클래스를 공식적으로 구현해야 합니다.

## 4. 🔗 의존성 및 패키지 관리의 공백

### 4.1. 현재 문제점
LLM이 `pandas`, `boto3` 등 서드파티 라이브러리를 사용하는 코드를 생성했을 때, 이를 메인 서버 환경에 동적으로 `pip install` 하는 것은 보안 및 인프라 파괴 행위입니다. 현재 이에 대한 처리 방안이 전무합니다.

### 4.2. 개선 방안
- **사전 정의된 베이스 이미지**: 데이터 분석용, 인프라 제어용 등 자주 쓰이는 의존성이 미리 설치된 별도의 도커 베이스 이미지 컨테이너를 준비합니다.
- **제한된 임포트 환경**: 샌드박스 환경 내부에서만 사용할 수 있는 화이트리스트 패키지 목록을 에이전트 프롬프트에 명시하여, 해당 범주 내에서만 툴 코드를 생성하도록 유도해야 합니다.

## 5. 🎯 결론 및 행동 강령 (Action Items)

현재의 Theseus 코어 시스템은 화려한 기능을 갖춘 '우수한 PoC(Proof of Concept)'에 가깝습니다. 실질적인 B2B 엔터프라이즈 프로덕션에 올리기 위해서는 **"새로운 기능 추가를 전면 중단하고, 핵심 아키텍처의 격리 및 안정화에 모든 리소스를 투입"**해야 합니다.

1. `custom_tools/` 파일 시스템 기반 로딩 구조 폐기 및 DB 기반 관리 체계 도입
2. DinD 또는 Serverless 기반의 Remote Execution 샌드박스 인프라 0순위 구축

4. Monkey-patch 코드를 걷어내고 어댑터 패턴으로 리팩토링

## 6. 🌐 타 언어(Java, C++) 확장 시나리오 분석 및 개선 프롬프트

현재 파이썬(Python) 기반으로 구축된 코어 엔진과 메타-툴링 시스템을 Java나 C++과 같은 컴파일 언어 환경으로 전환(또는 혼용)할 경우를 대비한 아키텍처적 솔루션과 프롬프트 엔지니어링 전략입니다.

### 6.1. 아키텍처 한계 및 솔루션 방향 (Polyglot & Remote Sandbox)
- **Java 환경**: 런타임에 소스코드를 동적 컴파일(`*.class`)하여 `ClassLoader`와 Reflection으로 로드하는 방식은 메타스페이스 OOM 및 기존 컨텍스트 충돌 위험이 매우 큽니다.
- **C++ 환경**: 공유 라이브러리(`.so`, `.dll`) 동적 로드는 치명적입니다. LLM이 작성한 C++ 코드에 댕글링 포인터 오류가 있다면 메인 서버 전체가 Core Dump를 남기며 종료됩니다.
- **최적의 솔루션 (언어 이종화)**: 메인 서버를 Java나 C++로 구축하더라도, 에이전트가 생성하는 **동적 도구는 Python, JavaScript, 또는 WebAssembly(WASM)** 로 생성하게 하여 별도의 샌드박스에서 실행(RPC/gRPC 통신)하는 Polyglot 아키텍처가 필수적입니다.

### 6.2. 컴파일 언어 적용 시 프롬프트(Prompt) 개선 필수 요건
만약 에이전트에게 불가피하게 Java나 C++ 코드를 생성하고 실행하게 해야 한다면, 기존 파이썬 기반 프롬프트(`_PLAN_EXECUTING_PROMPT_TEMPLATE`)에 다음과 같은 가드레일이 반드시 추가되어야 합니다.

1. **의존성(Dependency) 및 빌드 체인 강제**
   - *"도구 생성 시 단일 소스파일뿐만 아니라, 독립적 컴파일을 위한 빌드 스크립트(예: Maven `pom.xml` 또는 `CMakeLists.txt`)를 반드시 함께 제공하라."*
2. **엄격한 메모리 및 예외 처리(Exception Handling) 강제화**
   - *"작성하는 모든 함수는 `try-catch` 블록으로 보호하여 런타임 에러 발생 시 서버가 죽지 않도록 문자열을 반환하라."*
   - *(C++ 한정) "Raw Pointer 사용을 엄격히 금지하며, 동적 할당 시 `std::unique_ptr` 등 스마트 포인터만 사용하라."*
3. **컴파일 단계(Compilation Phase)의 명시적 분리**
   - *"코드를 작성한 후 즉시 실행하지 마라. `build_tool` 명령을 통해 먼저 컴파일을 시도하고, 컴파일 에러 발생 시 로그를 분석하여 코드를 수정하는 단계를 반드시 거쳐라."*
