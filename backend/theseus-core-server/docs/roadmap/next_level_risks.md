# Next-Level Risks & Roadmap (프로덕션 레벨을 위한 추가 분석 및 권고사항)

현재 Theseus 에이전트 시스템은 구조적으로 탄탄한 3-Mode 아키텍처와 Pydantic 기반 구조화된 출력, 그리고 AST 정적 분석 보안망을 갖추고 있습니다. 그러나 진정한 B2B 엔터프라이즈 레벨로 스케일업(Scale-up)하기 위해서는 다음 두 가지 주요 병목 현상에 대비해야 합니다.

## 1. 컨텍스트 윈도우 폭발 (Tool Schema Overflow)

### 현상
Session 4에서 OpenHarness의 37개 빌트인 도구 전체를 레지스트리에 자동 등록하도록 변경했습니다. 여기에 메타-툴링(`create_tool`)을 통해 동적으로 커스텀 툴들이 계속 추가되면, LLM에게 매 턴마다 전달해야 하는 **'도구 명세서(JSON Schema)'의 길이가 기하급수적으로 길어집니다.**

### 리스크
*   **비용 급증**: 매 API 호출마다 막대한 입력 토큰(Input Tokens)을 소모하게 되어 인프라 및 API 비용이 크게 증가합니다.
*   **성능 저하(Attention Loss)**: 모델이 너무 많은 도구 사이에서 주의력을 잃어, 상황에 맞지 않는 엉뚱한 도구를 선택하거나 환각(Hallucination)을 일으킬 확률이 높아집니다.

### 해결 제안: Tool Routing (Tool RAG) 체계 도입
향후 사용 가능한 도구가 50~100개를 넘어갈 경우, 모든 도구의 스키마를 System Prompt에 한 번에 쑤셔 넣는 방식은 폐기해야 합니다.
대신 에이전트의 현재 목표와 의도를 먼저 파악하여, **상위 5~10개의 관련 도구 스키마만 동적으로 프롬프트에 주입하는 툴 라우팅 체계(Tool RAG)** 도입을 로드맵에 반영해야 합니다.

## 2. AST 정적 분석의 한계 우회 (Dynamic Execution Bypass)

### 현상
Session 5에서 `ToolValidator`에 정적 코드 분석(AST) 방어 로직을 추가하여 명시적인 `import os`나 `shutil.rmtree`를 원천 차단했습니다. 하지만 파이썬은 실행 시간에 구조를 변경할 수 있는 매우 동적인 언어(Dynamic Language)입니다.

### 리스크
만약 악의적인 사용자나 극도로 환각을 겪는 LLM이 아래와 같이 우회 코드를 작성한다면, 단순한 구문 트리 검사(AST)로는 적발할 수 없습니다.

```python
# AST가 'os'나 'shutil' 임포트를 잡지 못하는 동적 우회 기법의 예시
module_name = 'o' + 's'
os_mod = __import__(module_name)
getattr(os_mod, 'system')('rm -rf /')
```
이러한 동적 실행 방식은 AST 노드 상으로는 `Import` 노드나 식별자(Identifier)에서 블랙리스트 키워드가 검출되지 않기 때문에 1차원적인 정적 분석을 무력화할 수 있습니다.

### 해결 제안: Sandboxing (Docker-in-Docker) 환경 분리
현재의 AST 검사는 LLM의 우발적인 실수나 기본적인 위험 로직을 막는 데는 매우 훌륭하고 가성비 좋은 방어책입니다. 그러나 B2B 환경에서 악의적인 사용자의 의도적인 공격을 막아내기에는 한계가 있습니다.
궁극적으로는 이전에 기획 단계에서 논의되었던 **Docker-in-Docker(DinD) 형태의 샌드박스(Sandbox) 실행 환경 분리**를 로드맵에 올려두고, 에이전트가 실행하는 모든 코드는 호스트 시스템과 완벽히 격리된 컨테이너 내부에서만 작동하도록 아키텍처를 진화시켜야 합니다.
